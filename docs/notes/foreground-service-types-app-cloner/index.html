Choosing honest foreground service types in an app cloner

Duo Clone declares a foreground service type for each kind of work it does in the background: specialUse for keeping copies running and for receiving push messages, dataSync for backup and restore, and, for services started by copied apps, the type the copied app asks for. Since version 0.1.36 each service declares the type that describes what it really does.

This note covers what Android and Google Play expect from a foreground service type, the type of each Duo Clone service and the reason for it, how a copied app's own foreground service is typed, and what happens when the phone restarts.

What do Android and Google Play expect from a service type?

An app that targets Android 14 must declare at least one foreground service type for each foreground service, and a permission for each type it uses. Android's page on required types says that a service without a type throws MissingForegroundServiceTypeException when it calls startForeground(). The page also says that a use case that matches none of the types should move to WorkManager or a user-initiated data transfer job, which is why the choice of type is a design decision and not a label.

Google Play adds its own step. Apps that target Android 14 and above declare the foreground service types they use in a declaration on the App content page of Play Console, and each type is subject to review. For dataSync backup and restore, Play's help page expects a feature that the user starts, and says that the demonstration cannot be "fully automatic or background backup or recovery". For specialUse it says to use it "in limited scenarios" where no defined type fits.

Which type does each Duo Clone service declare?

Four kinds of service run in the foreground, and each declares the type that matches its work.

The two specialUse services each carry the explanation that Android asks for in the manifest. The keep-running service says it "Keeps the apps the user opened inside Duo Clone running while the user switches to other apps", and the push service says it "Keeps the push message connection for apps the user runs inside Duo Clone, so they can show notifications while closed".

Why is keeping copies running not data sync?

Android defines dataSync as data transfer, such as uploads, downloads, and "backup-and-restore operations", and keeping a process alive is none of these. Using it for that purpose would also bring its time limit with it. For apps that target Android 15, the system lets dataSync services run for a total of 6 hours in a 24-hour period, then calls onTimeout() and expects the service to stop within a few seconds. That limit makes sense for a transfer. It would cut off a copy that is simply open.

The reverse holds for backup. A backup is a transfer that the user starts and that ends, so dataSync is the type Android's own description names for it, and the service stops when the transfer finishes. Backup and restore run in a service of their own, separate from the keep-running service.

How does a copied app's own foreground service get a type?

When an app in a copy starts a foreground service, Duo Clone passes the type the app asked for through to the system, if three conditions hold, and falls back to specialUse otherwise. The three conditions are:

  1. the helper service in Duo Clone's manifest declares that type;
  2. Duo Clone holds the matching FOREGROUND_SERVICE_ permission for it;
  3. the extra runtime condition that Android 14 sets for that type is met, such as location permission for a location service, camera permission for a camera service, or the microphone permission for a microphone service.

Two further rules keep the type honest. A copied app that does not declare dataSync never gets dataSync, so a music player is not typed as a data transfer. And if Android refuses the type the app asked for, for example because the app was started from the background without the camera or microphone being available, Duo Clone retries with specialUse, so the copy still stays alive instead of being stopped.

The helper services declare the set of types that copied apps commonly use: mediaPlayback, phoneCall, microphone, camera, location, dataSync and specialUse. A copied app that asks for a type outside that set gets specialUse.

What happens after the phone restarts?

Duo Clone does not start the keep-running service when the phone boots, and it never opens a copy on its own. After a restart no copy is running, so there is nothing to keep alive. Android 15 would also refuse some types here: a BOOT_COMPLETED receiver may not start dataSync, camera, mediaPlayback, phoneCall, mediaProjection or microphone services. The push service is the one Duo Clone does start after boot, and only when you have switched it on; specialUse is not on Android's list.

What else was trimmed?

The Google Play build declares no permission that copies never need. The changelog for version 0.1.36 lists payment, companion-device and system-settings permissions among those removed. The Settings item Allow background activity opens the system's own battery screen, where the choice is yours.

What should other developers take from this?

Pick the foreground service type by asking what the service does for the user, not what keeps it alive, and write the specialUse explanation as if a reviewer will read it. Check each type's runtime conditions and its time limit before you choose it, keep user-started work such as transfers in its own service, and test the restart and background-start paths on Android 14, 15 and 16, where the rules differ.
