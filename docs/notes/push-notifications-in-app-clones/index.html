Push notifications in app copies, including copies you have closed

Duo Clone 0.1.33 delivers push messages to the apps in your copies, and with the opt-in setting "Notifications from closed clones" it does so even when a copy is closed, using a foreground service and one silent notification. The message goes to the copied app itself, which posts its own notification, and Duo Clone adds the copy's name and number to the title so you can tell two copies of the same app apart.

This note explains how push works for an app that runs inside another app, why a closed copy needs a foreground service, what happens when the copy is locked, and how the scheduled background work of copied apps fits in.

How does a push message reach an app in a copy?

An app that uses Firebase Cloud Messaging receives each message in a service of its own, and in a copy that message has to be carried to the app by Duo Clone. Google's documentation describes the app side: the app extends FirebaseMessagingService and gets the message in onMessageReceived. On a normal install the phone's Google services hand the message over. Inside a copy, Duo Clone does that step, and it does not add a push server of its own: messages still travel through Google's push service, as they do for any app that uses it.

While a copy is running, the message goes straight to the app in that copy. This is why version 0.1.33 lists "Apps in copies can now receive push messages while they run" as its own change. For a closed copy there is nothing to hand the message to, which is the harder case.

Why does a closed copy need a foreground service?

Android lets an app hold a long-lived connection in the background only while it runs a foreground service with a visible notification, so receiving for closed copies means a persistent notification. Duo Clone keeps one connection for each Account while the setting is on. The notification is silent and reads "Receiving notifications for clones. Turn this off in Settings."

The service uses the foreground service type specialUse. Android describes that type as covering "any valid foreground service use cases that aren't covered by the other foreground service types", and asks the developer to describe the use in a manifest property that is reviewed when the app is submitted. Messages for a closed copy do not fit playback, location or data transfer, so specialUse is the honest type. The note on foreground service types covers how Duo Clone picks types for its other services.

The setting is off by default, and the line under it in Settings is plain about the cost: "Keeps a silent notification so apps in clones get messages while closed. Uses some extra battery." If your phone slows down or the battery drains, what a second copy of an app costs in battery and memory is covered in plain language on the Duo Clone website.

What happens when a message arrives for a closed copy?

Duo Clone starts the copy in the background, with no screen, passes the message to the app and lets the app post its own notification. The copy is then given a short time to finish, about a minute, and released if nothing else keeps it running. Google's FCM documentation is clear that onMessageReceived has "a short execution window" and that work which takes more than a few seconds must continue in a valid process lifecycle, so a copy that is released straight away would lose slow work.

Two kinds of copy are skipped on purpose:

  • A locked copy. If the copy sits behind the Private Space lock, the message is not delivered while it is locked, so the content of a message cannot be read out of a notification before you unlock. This is a limit: Duo Clone makes no promise about a message that arrives while the copy is locked.
  • An app that opts out of cloners. Apps that ask not to run in a virtual space, with the manifest property described in the REQUIRE_SECURE_ENV note, are not started.

What keeps the connection alive after a restart or an update?

When the setting is on, Duo Clone starts the service again after the phone boots and after Duo Clone itself is updated. An update stops a running service, and a reboot ends everything, so without this step notifications would stop silently until you opened the app. Android 15 forbids a BOOT_COMPLETED receiver from starting dataSync, camera, mediaPlayback, phoneCall, mediaProjection and microphone services. specialUse is not among them, so the push service may start at boot.

How does a notification say which copy it is from?

Duo Clone puts the copy's name and number before the notification title, for example "Chat #1 · Alex". The first version put this text in the notification's header line next to the app name. Some phone makers' interfaces do not show that header line for chat notifications, so the name moved into the title, the one text every notification shade shows. The name goes first because a long title is cut at the end. In a one-to-one chat the sender's name is the title, so the copy's name goes in front of the sender.

The name is the one you gave the copy, or the app's name if you did not, followed by the copy number. Text the app sets itself is kept after the copy's name.

What about scheduled background work?

Version 0.1.33 also runs the scheduled jobs of apps in copies, which is how WorkManager, JobIntentService and periodic jobs keep apps in sync. Google recommends WorkManager for work that has to persist. Duo Clone schedules those jobs for real, one set per copy, and cancels them when you use Clear data or delete the copy. Jobs also end the way Android ends them, so an app that waits for its background work to finish no longer hangs when you log out.

What should other developers take from this?

If you build a container that runs other apps, receiving push messages is a separate feature from running them, and it needs its own consent, its own foreground service and its own rules for locked and opted-out apps. Make the always-on part opt-in, say what it costs, label every notification with the copy it belongs to, and choose the foreground service type that matches the work.
